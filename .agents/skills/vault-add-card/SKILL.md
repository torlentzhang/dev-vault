# vault-add-card

在 `Notes/` 中新增一张原子知识卡，并将其接入现有知识结构。

本 Skill 自包含，定义新增知识卡的可执行流程与内容规范，按以下步骤执行。

## 步骤

### 1. 确定卡片类型

按知识性质选择模板：

| 知识性质 | 模板 | `type` | 落点 |
| --- | --- | --- | --- |
| 概念知识 | `concept-card.md` | `concept` | `Notes/` |
| 操作 / 配方 | `howto-card.md` | `howto` | `Notes/` |
| 书籍 / 文章 / 视频的摘录转述 | `literature-card.md` | `literature` | `Notes/` |

本 Skill 只处理写入 `Notes/` 的三类知识卡。`moc` 与 `daily` 类型不属本 Skill：MOC 创建或调整走重构流程，日记由用户直接记录。

不要自行创造未定义的卡片类型。

---

### 2. 检查已有卡片（委托子代理）

不得在主上下文凭印象判断「大概没有」，一律委托子代理检索 `Notes/`。

**委托任务**：检索 `Notes/`，判断是否已经存在相同主题卡片。

**返回**：

* 明确结论：有 / 无；没有就直说，不牵强关联
* 若有，区分**同一知识**（卡片名 + 重合点 + 是否可直接扩展）与**仅相关**
* 邻近卡片候选，供第 8 步建立关联

**边界（必须写进提示词）**：只读，不改任何文件；不判断 MOC 归属、不做命名；清单外的发现不回报；完成本步即收工，不得自行接着做下一步。

能够通过扩展已有卡片解决时，不创建重复知识。

**跳过规则**：由 `vault-learn-topic` 交棒进入时跳过本步——委托 A 已完成同一检索，结果随交棒材料到达。

---

### 3. 确定卡片名称与 Tags

知识卡优先使用**稳定、简洁、可检索的概念名称**，例如 `Promise`、`Event Loop`、`Corepack`、`pnpm`。优先按知识对象本身命名，而不是照搬用户的提问方式；避免 `xxx是什么`、`xxx怎么理解`、`xxx有什么用` 这类标题。

只有问题本身具有长期知识价值时才使用问题式命名，例如 `为什么需要 Corepack`。

Tags 是横向属性，不承担 MOC 分类职责，可表达技术领域、知识类型、学习状态、工具等。新增 Tag 前先检查是否已有语义相同或高度接近的 Tag，不使用 Tags 重复构建目录或 MOC。

---

### 4. 确定 Primary MOC

MOC 是导航地图，不是严格分类树。根据知识本质而不是知识的使用场景定位到现有 MOC：先读 `Index/Index.md` 的 L1 核心问题表，再沿 `Index/` 下的实际文件定位现有 L2 Subdomain 与 L3 Topic。已有 MOC 名称一律以实际文件为准，不凭记忆或举例创建新 MOC。

L2 是领域内部相对稳定的知识系统；L3 仅当某主题已形成独立知识地图时才创建。优先使用已有 MOC，不因为新增一张卡片就创建新的 MOC。创建新 MOC 需同时具备：

* 稳定的知识边界
* 独立的导航价值
* 长期增长可能
* 已存在多个相关知识主题
* 能形成独立内部结构

卡片数量只能辅助判断，不能机械触发创建。L3 偏大时优先使用 MOC 内部结构或拆分知识卡，不继续增加层级，也不为了让目录看起来完整而创建 MOC。

确定一个 `Primary MOC` 后，根据该 MOC 当前结构找到最合适的 `##` / `###` 分组。

例如：

```text
pnpm
→ MOC-Engineering-PackageManagement

Vue Router
→ MOC-Frontend-Vue-Router

Event Loop
→ MOC-JavaScript
```

一张知识卡不要求只能属于一个 MOC。如果同一张卡片对其他 MOC 也具有稳定的导航价值，可以被其他 MOC 引用，但不要复制卡片。

如果发现现有 MOC 结构本身需要重构，先说明现状、影响范围、迁移方案与回滚方式，取得用户明确确认后再执行；不在本 Skill 中顺手重构。

---

### 5. 落库前预览

写出任何文件之前，先把完整方案呈现给用户，等确认后再执行：

* **卡片全文**：把计划写入 `Notes/<卡片名>.md` 的完整内容呈现给用户（frontmatter + 正文 + 关联区），而不是只说「准备写一张关于 X 的卡」
* **拟修改文件清单**：卡片本身、Primary MOC（含落点小节）、以及是否需要连带调整索引
* **结构决策单独列出**：若落点需要新建 `##` / `###` 分组，或存在多个合理归属，单独说明请用户决定
* 用户确认后才开始写；要求修改时按意见调整，并**重新预览受影响的部分**

用户明确表示不需要预览时，可直接落库（视为已同意）。

---

### 6. 创建卡片

创建：

```text
Notes/<卡片名>.md
```

要求：

* 使用对应模板
* frontmatter 按模板填写，`type` 取步骤 1 表中的值
* 围绕单一知识主题，确保该主题可以作为独立知识单元被理解、复习和复用
* 不为追求原子化而机械拆分知识，不为同一知识创建多张卡片
* 不重复已有卡片内容
* 保持当前 Vault 的命名和内容风格
* 保留来源中的结构化表达：表格、目录树、编号步骤属于知识结构，不是排版装饰，不得降级为无序列表
* 正文只写结论，不写来源关系、版本考据与自我校正过程；来源只进 `source` 字段。反例：`MDN 写 A，某博客写 B，以 A 为准`、`v2 曾是 A，v3 改成 B`、`先写成 A，核对后改为 B`、`依据官方文档第 3 节`

---

### 7. 加入 MOC 导航

在 Primary MOC 的适当位置加入：

```markdown
- [[卡片名]]
```

优先加入现有小节。

如果该小节已经存在 `###` 分组：

> 加入最合适的现有分组。

不要为了单张新卡片自动创建新的 MOC 或新的 `###`。

---

### 8. 建立卡片关联

只建立真正有知识价值的关联。

优先考虑：

* 因果关系
* 前置 / 依赖关系
* 对比关系
* 互补关系
* 抽象与实现关系
* 原理与实践关系

在卡片末尾维护：

```markdown
## 关联
- [[相关卡片]] —— 一句话说明两者关系
```

卡片正文可按需使用 `[[...]]` 链接；`## 关联` 区只保留真正值得长期互链的精选关系。同一关系**只在一端登记**一句说明，链接本身双向可见，不需要两端都写。MOC 导航列表中的 `[[...]]` 不受此限。

---

### 9. 同步索引

检查相关导航与顶层 `Index/Index.md`：

* 新增卡片后，确认 Primary MOC 已引用该卡片
* 若卡片的加入改变了 MOC 结构，同步更新 `Index.md`

索引调整也需纳入步骤 5 的预览清单。

---

## 核实的边界

落库阶段是否需要核实，取决于入口：

* **接在 `vault-learn-topic` 之后建卡**：直接使用学习阶段已核实的结论，不重复核实。
* **未经学习、直接建卡**：核实本次要写下的断言。

直接建卡时按以下边界执行：

1. **先冻结断言清单**：列出本次要落下的每条断言，只核实清单上的项，清单外的疑点不查。
2. **按来源优先级核实**：官方规范 / 官方文档 > 官方源码 / 官方仓库 > 权威技术资料 > 社区资料。稳定且无争议的基础知识不必为形式强制联网验证。
3. **核实只读**：只做官方来源的只读比对，不得安装依赖、克隆仓库到本地或运行代码取结果，不自行搭建实验环境。
4. **有权威出处即收口**：官方 README / 官方文档已写清的事就是核实终点，不重复验证。
5. **矛盾不升级为阻塞**：文档、源码或用户提供的实测数据不一致时，只判断是否影响本次要落下的内容；不影响则标为存疑继续，影响则报用户决定。
6. **版本范围默认 stable**：RC / beta / canary 默认出界，除非用户点名；预发布版行为不得用于推断稳定版行为。
7. **抓取失败上限 2 次**：同一断言的抓取失败超过 2 次即标为「未核实」，不换通道死磕。

卡片中的「实测」结论只在用户提供实测数据、或用户明确点名要求实测时才写入。用户明确要求实测时，先说明操作、影响范围和回滚方式并取得确认；Agent 不自行决定搭实验环境。

### 未核实内容不落卡（硬规则）

**卡片正文、frontmatter 与关联说明中，都不得出现「未核实」的内容。**

无法确认是否走过学习流程时，**默认核实**。
