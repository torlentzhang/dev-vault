# vault-add-card

在 `Notes/` 中新增一张原子知识卡，并将其接入现有知识结构。

全局规则、权限、知识校验、MOC 架构、命名与关联区规则等以根目录 `AGENTS.md` 为准，本 Skill 只定义**可执行流程**，不重复定义原则。

## 步骤

### 1. 确定卡片类型

按 `AGENTS.md` 第 2 条的模板清单选择模板：

| 知识性质 | 模板 | `type` | 落点 |
| --- | --- | --- | --- |
| 概念知识 | `concept-card.md` | `concept` | `Notes/` |
| 操作 / 配方 | `howto-card.md` | `howto` | `Notes/` |
| 书籍 / 文章 / 视频的摘录转述 | `literature-card.md` | `literature` | `Notes/` |

本 Skill 只处理写入 `Notes/` 的三类知识卡。`moc` 与 `daily` 类型不属本 Skill：MOC 创建或调整走重构流程，日记由用户直接记录。

不要自行创造未定义的卡片类型。

---

### 2. 检查已有卡片

先搜索 `Notes/`，确认：

* 是否已经存在相同主题的卡片
* 是否存在明显重复卡片
* 当前需求是否只是已有卡片的补充
* 是否应该修改已有卡片，而不是新建卡片

能够通过扩展已有卡片解决时，不创建重复知识。

---

### 3. 确定卡片名称

按 `AGENTS.md` 第 7 条的命名规则确定名称：使用稳定、简洁、可检索的概念名称，优先按知识对象本身命名，而不是照搬用户的提问方式。

---

### 4. 确定 Primary MOC

根据知识本质定位到现有 MOC：

```text
知识本质
  ↓
L1 Domain（按 AGENTS.md 第 5 条的核心问题表）
  ↓
现有 L2 Subdomain（以 Index/ 下实际文件为准）
  ↓
现有 L3 Topic（如存在）
```

优先使用已有 MOC，不因为新增一张卡片就创建新的 MOC。MOC 的创建门槛见 `AGENTS.md` 第 5 条。

确定一个 `Primary MOC` 后，根据该 MOC 当前结构找到最合适的 `##` / `###` 分组。

例如：

```text
pnpm
→ MOC-Engineering-PackageManagement

Vue Router
→ MOC-Frontend-Vue-Router

Event Loop
→ MOC-JavaScript
```

如果同一张卡片对其他 MOC 也具有稳定的导航价值，可以被其他 MOC 引用，但不要复制卡片。

如果发现现有 MOC 结构本身已经需要重构，不在本 Skill 中顺手完成 MOC 重构：按 `AGENTS.md` 第 8 条的高风险流程，先向用户提出重构方案并取得确认。

---

### 5. 落库前预览

写出任何文件之前，先把完整方案呈现给用户，等确认后再执行：

* **卡片全文**：把计划写入 `Notes/<卡片名>.md` 的完整内容呈现给用户（frontmatter + 正文 + 关联区），而不是只说「准备写一张关于 X 的卡」
* **拟修改文件清单**：卡片本身、Primary MOC（含落点小节）、以及是否需要连带调整索引
* **结构决策单独列出**：若落点需要新建 `##` / `###` 分组，或存在多个合理归属，单独说明请用户决定
* 用户确认后才开始写；要求修改时按意见调整，并**重新预览受影响的部分**

用户明确表示不需要预览时，可直接落库（视为已同意）。

---

### 6. 创建卡片

创建：

```text
Notes/<卡片名>.md
```

要求：

* 使用对应模板
* frontmatter 按模板填写，`type` 取步骤 1 表中的值
* 围绕单一知识主题
* 不重复已有卡片内容
* 保持当前 Vault 的命名和内容风格

---

### 7. 加入 MOC 导航

在 Primary MOC 的适当位置加入：

```markdown
- [[卡片名]]
```

优先加入现有小节。

如果该小节已经存在 `###` 分组：

> 加入最合适的现有分组。

不要为了单张新卡片自动创建新的 MOC 或新的 `###`。

---

### 8. 建立卡片关联

只建立真正有知识价值的关联。

优先考虑：

* 因果关系
* 前置 / 依赖关系
* 对比关系
* 互补关系
* 抽象与实现关系
* 原理与实践关系

在卡片末尾维护：

```markdown
## 关联
- [[相关卡片]] —— 一句话说明两者关系
```

关联默认**只在一端登记**（链接本身双向可见），规则见 `AGENTS.md` 第 6 条。

---

### 9. 同步索引

按 `AGENTS.md` 第 9 条检查相关索引，包括顶层 `Index/Index.md`：

* 新增卡片后，确认 Primary MOC 已引用该卡片
* 若卡片的加入改变了 MOC 结构，同步更新 `Index.md`

索引调整也需纳入步骤 5 的预览清单。

---

## 核实的边界

落库阶段是否需要核实，取决于入口：

* **接在 `vault-learn-topic` 之后建卡**：直接使用学习阶段已核实的结论，不重复核实；其中标为「存疑 / 未核实」的项，在卡片中保留同样标注。
* **未经学习、直接建卡**：按 `AGENTS.md` 第 4 条的来源优先级，核实本次要写下的断言；停止条件（冻结断言清单、有出处即收口、抓取失败上限 2 次等）同样适用。

**核实只读**（`AGENTS.md` 第 4 条）：核实只做官方来源的只读比对，**不得安装 npm 包、克隆仓库到本地或运行代码取结果**。官方 README / 官方文档已写清的事就是核实终点。卡片中的「实测」结论只在用户提供实测数据、或用户明确点名要求实测时才写入，后者按第 8 条 R2 走确认流程——Agent 不自行决定搭实验环境。

任一情形下，清单外的疑点都只有两个出口——在卡片中按 `AGENTS.md` 第 4 条的术语（已核实 / 存疑 / 未核实）如实标注，或提给用户决定；不在本阶段做跨版本溯源。

无法确认是否走过学习流程时，**默认核实**。
