# 服务端渲染（SSR）

## 一句话定义
SSR（Server-Side Rendering，服务端渲染）是在服务端把组件渲染成 HTML 字符串直接发给浏览器，浏览器先显示这份 HTML，等 JS 到达后再把它**水合（hydration）**成可交互应用。

## 用于解决什么问题
纯 CSR 应用发给浏览器的是一份空壳，内容要等 JS 下载并执行后才出现。SSR 把「生成 HTML」这一步挪到服务端，换来两件事：首屏内容更快可见，以及爬虫/分享预览拿到的是带内容的 HTML 而不是空壳。

## 要点

### 核心是水合，不是重新渲染
客户端挂载 SSR 应用时**不会**重建 DOM，而是按组件树认领已有节点、只补事件监听。所以服务端与客户端的渲染结果必须严格一致，否则会出现内容闪烁或事件绑错节点。

### 渲染模式是一条光谱，不是二选一
区别只在「HTML 什么时候、由谁生成」：

| 模式        | HTML 何时生成         | 定位             |
| --------- | ----------------- | -------------- |
| CSR       | 浏览器里，JS 执行后       | 首屏空壳，之后全在客户端   |
| SSR       | 每次请求时在服务端         | 内容可实时、可因人而异    |
| SSG       | 构建时一次性生成          | 内容人人相同且构建时确定   |
| ISR / SWR | 构建时生成 + 按 TTL 再生成 | 静态速度 + 定期刷新    |
| 流式 SSR    | 服务端分段发送           | 不等整页拼完，先发已就绪部分 |
| 边缘渲染      | CDN 边缘节点上         | 缩短渲染机到用户的距离    |

SSG 的适用条件是**每个用户看到的都一样**——内容因人而异（登录态、个人推荐）时构建期拿不到那份数据，改用 SSR。Nuxt 里「静态生成」不是与 universal/CSR 并列的模式名，而是 Prerendering 单独成页 + `prerender` route rule。

### 别把 CSR 和 SPA 当成同一件事
两个词回答的是不同问题，可以交叉组合：

| 概念 | 回答的问题 | 取值 |
| --- | --- | --- |
| **CSR / SSR / SSG** | HTML 在哪里、什么时候生成 | 浏览器 / 请求时的服务端 / 构建时 |
| **SPA / MPA** | 换页面要不要整页刷新 | 不刷新 / 刷新 |

MDN 对这条区分有明确表述：「single-page applications **do not require** the site to be CSR」——现代框架可以做出「具备 SSR 能力的 SPA」。

所以一个应用完全可以两端各占一个标签：**首屏由服务端生成（SSR/SSG），站内跳转不刷新（SPA）**。Nuxt 默认就是这个形态。只有「默认脚手架 + 纯静态托管」这种最常见组合，才恰好同时是 CSR 和 SPA。

判断时看「查看网页源代码」而不是 DevTools 的 Elements 面板——后者显示的是 JS 执行后的 DOM，任何模式下都已填满。

### 收益：首屏可见更快，但可交互不变快
SSR 优化的是 **FCP（内容可见）**：HTML 一到就能显示。但 JS 仍要下载、执行，再多一道水合，按钮才真能点——**可交互时间不变，甚至略慢**。想连交互一起快，得减少需要水合的 JS，那是另一个话题。

### SEO：不是「SSR 才有 SEO」，而是「爬虫不等待」
Vue 官方把 Better SEO 列为 SSR 优势，但同一节的限定才是关键：Google 和 Bing 能正常索引**同步**渲染的 JS 应用，**同步**是关键词；如果应用先弹 loading 圈再 Ajax 取内容，爬虫不会等你跑完。

MDN 口径一致：主流搜索引擎能执行 JS，纯 CSR 站点**仍可被索引**；但**社媒爬虫通常不能**。所以分享预览卡片是硬约束——微信、Twitter、Slack 基本只读服务器返回的那份 HTML。

推论：**需要的是「逐 URL 的 HTML」，不是「SSR」本身。** SSG 一样能满足，而且更便宜。纯 CSR 做不到的是「不同 URL 返回不同 HTML」——服务器对所有路径都返回同一份 `index.html`，meta 标签只能写一套。

### 代价
- 需要跑得动 Node/JS 的服务进程，不能纯静态托管
- 每请求渲染一次，服务器压力与成本
- 代码要能在服务端跑：`window`、`document`、`localStorage` 都不存在
- 服务端/客户端渲染不一致会导致水合错配
- 因人而异的页面难直接丢 CDN 缓存
- 性能问题可能出在服务端也可能在客户端，排查面变宽

### 混合渲染：不必全站二选一
Nuxt 用 route rules 按路由分配策略，营销页走 SSG、后台走 CSR、商品页走 ISR 可共存：

```ts
routeRules: {
  '/': { prerender: true },
  '/blog': { isr: 3600 },
  '/products': { swr: true },
  '/admin/**': { ssr: false },
}
```

全站切成纯客户端渲染就是 `nuxt.config.ts` 里的 `ssr: false`。官方对该项的说明直白点出 SSR 提供了什么：「If set to `false` generated pages will have no content.」

### 选型判据
1. 内容人人相同且构建时确定 → SSG，能用就别上 SSR，运维成本差一个量级
2. 内容实时或因用户而异，且必须被搜索引擎/分享卡片读到 → SSR 或 ISR
3. 内容实时但只在登录后可见（后台、内部工具）→ 纯 CSR 就够
4. 内容偶尔变、流量不大 → 构建时渲染 + 静态托管最划算

最常见的错配：为了「SEO 好」上 SSR，但项目根本没有公开的、需要被搜到的页面。后台系统上 SSR 只是为不需要的收益付服务器账单。

## 我的理解 / 类比
SSR 不是「重新做一个应用」，而是**把「生成 HTML」这一步从浏览器挪到服务器**。像餐厅：CSR 是把食材和菜谱一起打包给你，你回家自己做，等待时间长但之后随便改；SSR 是厨房先做好端上来，你马上能看见菜，但餐具（JS）还得等送到、摆好（水合）才能开动。

「首屏快」和「能交互」是两件事，SSR 只买了前者。
