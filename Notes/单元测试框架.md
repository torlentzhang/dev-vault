# 单元测试框架

## 一句话定义
单元测试框架负责三件事：**组织**用例（describe / it）、**断言**结果（expect）、**隔离**依赖（mock）。Vitest / Jest / Mocha 的差别主要在「和构建链的关系」与「开箱程度」。

## 用于解决什么问题
没有框架时，跑一遍测试要自己写脚本、自己比对结果、自己模拟依赖；换个人接手，先得读懂这套自制脚手架。

## 要点

### 三者定位
| 框架 | 定位 | 代价 |
| --- | --- | --- |
| Vitest | 基于 Vite 的测试框架 | 绑定 Vite 生态 |
| Jest | 开箱即用、生态成熟 | ESM 支持实验性，需额外配置 |
| Mocha | 灵活、可自由组合断言库与 mock 方案 | 配置量大，得自己拼 |

### Vitest 与 Vite 的关系
官方原文：*Vitest reads your `vite.config.*` by default, so your existing Vite plugins and configuration work out-of-the-box.* 它复用同一套配置与转换管线——dev、build、test 共用一条链路，所以 Vite 项目里几乎不用额外配置。官方章节标题直接写作 *The Need for a Vite Native Test Runner*。

### Vitest 与 Jest 的兼容性
- 官方说法是「兼容**大部分** Jest API」：*compatibility with most of the Jest API and ecosystem libraries … a drop-in replacement for Jest*
- `expect` 与 mock 都是 Jest 兼容的（`vi` 对象提供 `jest` 兼容 API）
- 有官方迁移专章，页首写明 *designed with a Jest compatible API, in order to make the migration from Jest as simple as possible*
- **差异确实存在**：该迁移专章逐条列出了 globals 默认值、`mock.mockReset`、mock 持久性、模块 mock、自动 mock 行为、定时器、hooks、类型等条目，是迁移时要核对清单

另需留意：官方把 watch 模式、浏览器模式、基准测试列在**能力清单**（features）里，而不是「与 Jest 的差异」清单——两处不要混为一谈。

### Jest 的现状
- 当前文档版本 30
- **ESM 支持为实验性**：官方原文 *Jest ships with experimental support for ECMAScript Modules (ESM). The implementation may have bugs and lack features.* 启用需要关掉 transform 并让 node 带 `--experimental-vm-modules` 运行
- 结论：纯 ESM 的现代项目里，这是会实际挡路的一项，不是理论问题

### 怎么选
- 已经是 Vite 项目 → **Vitest**，配置复用是白拿的好处
- 老旧 CJS 项目、或团队已在 Jest 上积累 → **Jest**，迁移成本常大于收益
- 需要非标准组合（自己挑断言库 / mock / reporter）→ **Mocha**

## 我的理解 / 类比
Vitest 是**和你的工地拉同一根电线**（不用重新布线）；Jest 是**自带完整配电箱的成品房**（拎包入住，想改线得先研究它的配电逻辑）；Mocha 是**散件**——什么都能装，什么也都得自己装。
