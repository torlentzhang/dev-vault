# SSR 双端构建

## 一句话定义
SSR 应用要同时产出两份构建结果——服务端产物与客户端产物。两者来自**同一份应用源码**，但面向不同运行环境，由不同目标编译，产物形态也不同。

## 用于解决什么问题
服务端要的是渲染成 HTML 的能力，客户端要的是操作 DOM、响应交互的能力。一份源码无法同时满足，所以必须各编一次。理解这点才能明白 SSR 项目的构建配置为何总有两套入口。

## 要点

### 共享的是源码，不是产物
Vite 文档给出的典型结构把职责拆得很清楚：

```
index.html
server.js            # 应用服务器
src/
  main.js            # 与环境无关的通用应用代码
  entry-client.js    # 把应用挂载到 DOM
  entry-server.js    # 用框架的 SSR API 渲染应用
```

两端各有独立入口，都引用同一个「通用代码（universal code）」。

### 工厂函数而非单例
通用代码导出的是**创建应用的工厂函数**，不是已创建的实例。原因在 Vue 文档的「跨请求状态污染」：SSR 下应用模块通常只在服务器启动时初始化一次，同一份模块实例会跨请求复用；若用单例状态，某个用户的数据会泄漏给另一个用户的请求。

### 编译产物形态不同（以 Vue 为例）
Vue 文档明确：SSR 下组件的编译产物不同，「模板被编译为字符串拼接而不是 render 函数，以此提高渲染性能」。

| | 客户端 | 服务端 |
| --- | --- | --- |
| 产物形态 | render 函数（虚拟 DOM） | 字符串拼接 |
| 为何如此 | 需要 diff、需要响应更新 | 一次性拼出 HTML，无更新需求 |

服务端不存在 DOM 更新，虚拟 DOM 那一层没有收益，所以直接拼字符串。

### 因此构建要做两套
Vite 文档：「we will need to coordinate two builds for the same app: one for the client, and one for the server.」

这是 SSR 项目构建配置比 SPA 复杂一档的根本原因：目标环境（浏览器 / Node）、输出目录、入口都要分两套。

### 不借助构建工具时的退化形态
手工搭 demo 时，容易把组件定义在服务端和客户端各写一遍。这等于把「一份源码」退化成两份副本——两端一旦不同步就是水合不匹配。双端构建要消除的正是「需要人工保持一致」这件事。

## 我的理解 / 类比
像一份菜谱出两个版本：给厨房看的是分步操作指令（服务端，目标是尽快端出成品），给顾客看的是能自己调整口味的自助终端（客户端，目标是可反复互动）。菜谱内容是一份，译成两种用途的语言。
