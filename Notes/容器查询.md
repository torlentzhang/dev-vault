# 容器查询

## 一句话定义
容器查询是按**最近的查询容器祖先**的尺寸（而不是视口）条件应用样式，让组件在任意容器里自适应。

## 要点

### 它解决什么问题
媒体查询按**视口**判断：同一个卡片组件放进侧边栏或主内容区，**视口没变、可用宽度却变了**，媒体查询的结论立刻失效——同一个组件要么在侧栏里挤成一团，要么在主区域里浪费空间。

```html
<main>   <!-- 视口 ≥1024px，主区域可用宽度很大 -->
  <article class="card">…</article>   <!-- 理想：横排 -->
</main>
<aside>  <!-- 视口不变，但侧栏只有 280px -->
  <article class="card">…</article>   <!-- 理想：竖排 -->
</aside>
```

改用容器查询后，卡片按**自己容器的宽度**决定横排还是竖排：**组件搬到哪里都对**，不再关心自己在页面哪个位置、视口有多宽。这也是它在组件文档里能做「开关式演示」的原因——拖动容器宽度就能看到组件各档形态。

### container-type 取值
`container-type` 决定「按哪个轴、能查询什么」：

| 取值 | 含义 |
| --- | --- |
| `normal` | 默认。仅可用于 **style 查询**与 name-only 查询 |
| `size` | 两个轴，应用 **size 包含** |
| `inline-size` | 仅 inline 轴，应用 style + **inline-size 包含** |
| `scroll-state` | 滚动状态类查询 |
| `anchored` | 锚定（anchor）相关查询 |

> ⚠️ 存疑：`scroll-state` 与 `anchored` 的浏览器支持情况本次**未逐条核实**，不要按上面的「widely available」对待。

### ⚠️ inline-size 的坑（重点）
`container-type: inline-size` 在让元素成为查询容器的同时，会对它施加 **inline-size 包含**，后果是一串连锁反应：

- 元素的 **inline 尺寸不能再由内容撑开**——内容不参与内在尺寸计算；
- 尺寸**必须由外部给出**（`width` / flex / grid）；
- `width: auto` 的父级或网格自动列**可能塌缩**；
- 也**不能再用内容做 `min-content` 收缩**。

```css
.panel { container-type: inline-size; }   /* 声明：我是查询容器 */
@container (width >= 400px) {
  .card { display: flex; }                /* 容器够宽才横排 */
}
```

```html
<!-- 危险组合：父级 width:auto + 子级 inline-size 包含
     父级可能失去"被内容撑开"的宽度而塌缩 -->
<div class="panel">
  <article class="card">…</article>
</div>
```

一句话记法：**让一个元素「按容器宽度自适应」，你就得先替它把宽度决定好**——别再指望内容帮你撑。

### 与本库已有结论的接缝
[[断点变体]] 里记过一条典型混淆：**`@sm:` 在两家含义不同**。

| 写法 | Tailwind | UnoCSS |
| --- | --- | --- |
| `@sm:` | **容器查询**：按父容器宽度（父元素需加 `@container`），与视口无关 | **显式媒体查询**：等价于 `sm:`（视口 ≥640px） |
| `~sm:` | 无此写法 | 容器查询变体 |

所以看到 `@` 前缀先确认框架：Tailwind 里它问的是「**你这个房间多大**」，UnoCSS 里它问的还是「**整栋楼多高**」。

## 我的理解 / 类比
- 媒体查询是「按**整栋楼的高度**决定装修」，容器查询是「按**你这个房间的大小**决定装修」。
- 组件不该关心自己在哪栋楼里：一张卡片被放进主区域还是侧栏，是**使用者的选择**，组件无从预知——容器查询把决定权交还给「房间」。
- `inline-size` 包含像「你要求按房间大小装修，就得先有人把墙砌好」：墙（宽度）没定，装修方案无从谈起。
