# 依赖升级评估

## 适用场景
- 准备做大版本（major）依赖升级时，先评估破坏性变更与影响面，避免「无脑全升后 build 炸一片」。
- 也适用于 minor/patch 批量升级前的体检；尤其当依赖被钉死为确切版本（无 `^`/`~`）时，需用 `-L` 才能突破范围升级。
- 本卡是一份可复用的评估流程，回答「升级前怎么评估」；「用哪条路径去更新」见 [[npm依赖更新方法]]。

## 步骤
1. **快照现状**：读 `package.json` / 锁文件，确认当前版本与版本范围写法（确切版本 vs semver 范围），并把当前可工作状态 commit 一个回滚点。
2. **查官方迁移指南**：搜 `<包名> vX migration guide` / `BREAKING CHANGES` / `MIGRATION.md`，以官方第一手来源为准（以官方博客与仓库为准，警惕标题党式二手解读）。
3. **读 changelog 圈重点**：看从当前版本 → 目标版本之间所有 major/minor 的 breaking 条目；跨多代升级要连续看累加。
4. **评估依赖链 / peer 兼容**：谁依赖它？它的 `peerDependencies` 要求什么？用 `pnpm why <pkg>`、`npm view <pkg>@<ver> peerDependencies` 排查连带影响。
5. **隔离 + 分批**：一次只升一个大版本包，升完即验证，出问题能精准定位。
6. **升级后验证矩阵**：`build` + `type-check` + `test` + `lint` 全跑一遍。**聚合脚本要拆开定位失败步骤**——若某步实为 `run-s "lint:*"` 之类的串联脚本，需分别跑各子命令，才能判断是哪一步挂、失败是否与本次升级相关。
7. **回滚预案**：升级前先 commit / stash，炸了能一键回去。用全量 `-L` 追最新版时，若目标包自身或周边工具生态未跟上（缺少稳定 API、尚未适配新版本），依赖它的工具可能直接崩溃——这也是要隔离升级的原因。

## 注意事项 / 踩坑
- **钉死确切版本 ≠ 已最新**：`pnpm up`（无 `-L`）只看 `package.json` 的范围，确切版本（如 `"vue": "3.5.41"`）会让 `pnpm up` 误报「All up to date」；`pnpm outdated` 才是真实体检。
- **大版本升级看 `latest` 而非范围**：`pnpm up -L`、`npm-check -u` 都会突破范围追 `latest`，但 `npm-check -u` 底层跑 npm、不更新 `pnpm-lock.yaml`，混用会致锁文件错乱——pnpm 项目请用 `pnpm up -L`。
- **实测优先于猜测**：资料查完仍要跑验证矩阵拿真实 exit code，光凭推断不可靠；且要**区分失败归属**——聚合命令失败未必由本次升级引起，可能先被无关的原有问题（既有 lint 错误、既有测试失败）中断，导致根本没跑到受升级影响的那一步。
