# 组件测试的输入与输出

## 一句话定义
组件测试只该断言**用户能观察到的东西**：输入（props、交互、数据流）与输出（渲染出的 DOM、emit 的事件、副作用）。其余一律是实现细节。

## 用于解决什么问题
一个组件改内部实现（换变量名、抽子函数、换状态管理方式）时，测试不该跟着挂。没有这条判据，测试就会写成「断言内部某个变量等于 2」，重构一次全红——测试从保护变成负担。


## 要点

### 输入与输出清单
| | 内容 |
| --- | --- |
| **Inputs** | Props（组件收到的参数）、Interactions（点击、输入等「人的」交互）、Data streams（接口数据、订阅） |
| **Outputs** | DOM elements（渲染出来的节点）、Events（`$emit` 的事件）、Side effects（`console.log`、接口调用） |

### 测 props
挂载时用 `props` 选项；测试过程中用 `setProps()` 改，**必须 `await`**（官方原话：*to ensure that the DOM has been updated before the assertions run*）。

```js
const wrapper = mount(MyButton, { props: { type: 'primary', disabled: false } })
expect(wrapper.html()).toContain('...')

await wrapper.setProps({ disabled: true })
expect(wrapper.attributes('disabled')).toBeDefined()
```

- 读当前 props：`wrapper.props()`
- 枚举型 prop（variant / size / disabled 这类）**每种取值各断言一个可观察结果**，不要只测默认值
- ⚠️ `data` 挂载选项**只对 Options API 生效**；`<script setup>` 组件要用 `setValue` / `trigger` 改状态

### 测 slots
挂载时用 `slots` 选项，支持多种形态：

```js
import { h } from 'vue'
import Bar from './Bar.vue'

mount(MyCard, {
  slots: {
    default: 'Default',                  // 字符串（也可给数组）
    first: h('h1', {}, 'Named Slot'),    // 渲染函数
    second: Bar                          // 直接给 SFC
  }
})
```

官方支持的写法：字符串、数组、`h()` 渲染函数、`{ template: '...' }` 对象、导入的 `.vue` 组件。

**断言渲染结果，不要断言 slot 对象：**

```js
expect(wrapper.html()).toContain('Default')
expect(wrapper.find('main').text()).toContain('Main Content')
```

作用域插槽用 `<template #default="params">` 包裹；不包裹时作用域以 `params` 对象暴露。

**`scopedSlots` 已废弃**：官方迁移页原话 *the `scopedSlots` mounting option is now deprecated - just use the `slots` mounting option for everything.* Vue 3 把 slot 与 scoped-slot 合并成 `v-slot` 一套语法，挂载选项也随之统一。

### 测事件
`wrapper.emitted()` 返回所有已 emit 的事件；`emitted(eventName)` 返回数组，每个元素是一次 emit 的参数数组：

```js
expect(wrapper.emitted()).toHaveProperty('change')

const changes = wrapper.emitted('change')
expect(changes).toHaveLength(2)
expect(changes[0]).toEqual([{ value: 'a' }])
```

交互一律用 `trigger()` 模拟，再断言 emit 结果——这才是「从用户视角验证」。

### 测 attrs（组件允许透传时）
透传属性是契约的一部分，应一起测：

```js
const wrapper = mount(MyButton, { attrs: { id: 'submit-btn', disabled: true } })
expect(wrapper.attributes()).toEqual({ id: 'submit-btn', disabled: 'true' })
```

官方注明一条规则：**显式声明的 prop 会覆盖同名 attribute**——

```js
mount(Component, {
  props: { message: 'Hello World' },
  attrs: { message: 'this will get overridden' }
})
// wrapper.props()       → { message: 'Hello World' }
// wrapper.attributes()  → {}
```

### 应当避免的写法
官方点名的反例：用 `setData()` 改内部数据 + 依赖 `.paragraph` 类名断言样式，被明确标为 **false positive**。

| ❌ 测实现细节 | ✅ 测输入输出 |
| --- | --- |
| `setData({ count: 2 })` 后断言内部状态 | 传 `props` 后断言渲染结果 |
| 断言内部方法被调用 | 断言 `emitted()` 里的参数 |
| 依赖 `.paragraph` 这类内部类名 | 断言用户可见文本或语义元素 |
| 断言 slot 在内部如何被组织 | 断言 slot 内容最终渲染出来了 |

## 我的理解 / 类比
把组件当成**一台有面板和指示灯的机器**：旋钮和按钮是输入（props、交互），读数表和亮灯是输出（渲染结果、事件）。检查这台机器，就该**拧旋钮、看读数**——而不是拆开外壳去看里面那根连杆是不是转到了 37 度。外壳（内部实现）换代升级时，旋钮和读数没变，说明书就不该重写。
