# 前端测试分类

## 一句话定义
测试按**被测对象的粒度**分层：单元（单个函数 / 组件）→ 集成（组件之间）→ e2e（整个系统）。粒度越细越便宜、跑得越快、失败定位越准；粒度越粗越接近真实用户，但慢、脆、难定位。

## 用于解决什么问题
写完功能不确定能不能跑、加功能怕碰坏别处、重构后问题频出——这三件事的共同解法都是「用自动化的检查把已知行为固定下来」，而分层决定了该在哪一层写什么检查。

## 要点

### 三个维度：全面 / 持续 / 自动化
- **全面**：覆盖正常路径之外的分支——边界、空值、异常、权限
- **持续**：每次提交都跑，而不是等到发版前
- **自动化**：能重复执行、不依赖人工点按，否则「持续」不成立

三者不是并列的选项，而是**互为前提**：不自动化就做不到持续；不全面则持续地在跑错的检查。

### 六类测试
| 类型 | 测什么 | 粒度 |
| --- | --- | --- |
| 单元测试 | 单个组件或函数 | 最细 |
| 集成测试 | 组件之间的交互 | 中 |
| e2e（端到端） | 整个系统跑通一条真实路径 | 最粗 |
| 性能测试 | 应用在高负载下是否正常运行 | 横切 |
| 可用性测试 | 用户体验是否易用 | 横切 |
| 兼容性测试 | 各设备与浏览器上是否正常 | 横切 |

前三类是**分层**（粒度从细到粗，顺序也是推荐顺序：先单元、再集成、最后 e2e）；后三类是**横切关注点**，不占某一层，而是每一层都要问一遍。

### 为什么顺序不能倒
- 单元测试跑得最快、失败时能直接指到函数，是最廉价的防线
- e2e 最接近真实，但慢、依赖浏览器与网络、失败时只能告诉你「某处坏了」
- 倒过来（只写 e2e）会让每次提交都等很久，且一个改动引发一片飘红却无法定位

## 我的理解 / 类比
像**造房子验收**：单元测试是检查每块砖（便宜、能换）；集成测试是检查墙砌得对不对（砌法和砖之间的咬合）；e2e 是人住进去走一遍全屋水电气。只做最后一项，等于等住进去才发现某块砖是空的。
