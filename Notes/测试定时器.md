# 测试定时器

## 一句话定义
测 `setTimeout` / `setInterval` / 延时逻辑时，不用真的等——用 `vi.useFakeTimers()` 把定时器换成假的，再手动推进虚拟时间，测试瞬间就能跑完本该等 3 秒的逻辑。

## 用于解决什么问题
真实等待既慢又不稳：等 3 秒的测试跑一百遍就是五分钟，且受机器负载影响。假定时器把「时间」变成可编程的输入，让「1 秒后会发生什么」变成一次确定的断言。

## 要点

### 四个基本动作
```js
vi.useFakeTimers()              // 启用假定时器
vi.advanceTimersByTime(1000)    // 推进虚拟时间
vi.useRealTimers()              // 恢复真实定时器
vi.setSystemTime(new Date(...)) // 只改「现在几点」
```

最简写法：

```js
beforeEach(() => { vi.useFakeTimers() })
afterEach(() => { vi.useRealTimers() })

it('延迟 1 秒后执行', () => {
  const fn = vi.fn()
  setTimeout(fn, 1000)

  expect(fn).not.toHaveBeenCalled()
  vi.advanceTimersByTime(1000)
  expect(fn).toHaveBeenCalledOnce()
})
```

`advanceTimersByTime` 的语义：**触发所有已排定的定时器，直到走完指定毫秒数或队列为空，二者先到为止**。所以推进不足不会触发：

```js
setTimeout(fn, 1000)
vi.advanceTimersByTime(999)
expect(fn).not.toHaveBeenCalled()   // 还差 1ms
vi.advanceTimersByTime(1)
expect(fn).toHaveBeenCalledOnce()
```

### 完整 API：同步 5 个 + 异步 4 个
| 同步（返回 `Vitest`） | 异步（返回 `Promise<Vitest>`） |
| --- | --- |
| `advanceTimersByTime(ms)` | `advanceTimersByTimeAsync(ms)` |
| `advanceTimersToNextTimer()` | `advanceTimersToNextTimerAsync()` |
| `advanceTimersToNextFrame()` | —— |
| `runAllTimers()` | `runAllTimersAsync()` |
| `runOnlyPendingTimers()` | `runOnlyPendingTimersAsync()` |

辅助工具：`clearAllTimers()`、`getTimerCount()`、`isFakeTimers()`、`getMockedSystemTime()`、`getRealSystemTime()`、`runAllTicks()`。

`advanceTimersToNextTimer()` 一次只跑下一个定时器，适合「每个定时器之间要做断言」的场景；`advanceTimersToNextFrame()` 推进到 `requestAnimationFrame` 需要的时间。

### 同步 / 异步变体的区别
官方对异步变体的表述：

- `advanceTimersByTimeAsync`：*…This will include asynchronously set timers.*
- `advanceTimersToNextTimerAsync`：*Will call next available timer and wait until it's resolved if it was set asynchronously.*
- `runAllTimersAsync` / `runOnlyPendingTimersAsync`：*…even asynchronous timers / ones.*

**经验性结论**：定时器回调里若有 `await` / Promise 链，同步变体只执行到第一个 `await` 就返回，此时断言会落空；应改用异步变体并 `await`。

```js
// 回调是 async 时，用异步变体更稳
await vi.advanceTimersByTimeAsync(1000)
expect(result).toBe('done')
```

> ⚠️ 这是**经验性结论**，不是官方明文规则。官方只在异步 API 上写了「会等异步定时器」，**没有**把它抽象成「推进时间后必须冲刷微任务」的通则（`guide/mocking/timers` 全文没有 `await` / `Promise` / `microtask` 字样）。判断依据：同步变体返回 `Vitest`，异步变体返回 `Promise<Vitest>`。

### `setSystemTime`：改「现在几点」，不推进定时器
官方原文：*If fake timers are enabled, this method simulates a user changing the system clock (will affect date related API like `hrtime`, `performance.now` or `new Date()`) - however, it will not fire any timers. If fake timers are not enabled, this method will only mock `Date.*` and `Temporal.Now.*` calls.*

两种情况分清楚：

| 场景 | 用什么 |
| --- | --- |
| 测「跨天 / 跨月」这类日期分支 | `vi.setSystemTime()`——只改时钟，不跑定时器 |
| 测「3 秒后刷新」这类时间推移 | `vi.advanceTimersByTime()`——推进时钟并触发定时器 |

用 `advanceTimersByTime` 推进一天，会顺带跑掉这一天里排着的所有定时器——这通常不是你要的。

⚠️ 官方另有一条提醒：*This value will not automatically reset between different tests.* 必须在 `afterEach` 里 `vi.useRealTimers()`，否则日期 mock 会串到后续测试。

### 假定时器与 `vi.waitFor` 是协作关系，不是二选一
官方原文：*When fake timers are enabled, these APIs advance them while they run: `vi.waitFor` and `vi.waitUntil` advance timers by `interval` before every check. `expect.poll` advances timers by `interval` after every failed attempt.*

也就是说：假定时器开着时，`waitFor` / `waitUntil` / `expect.poll` 会**自动推进时间**，基于 `setTimeout` 的被测代码照样能被兜到。不需要为了等异步结果而关掉假定时器。

`waitFor` 与 `waitUntil` 的差别：

| | 回调抛错时 |
| --- | --- |
| `vi.waitFor` | 继续重试，直到成功或超时 |
| `vi.waitUntil` | 立即中断并报错（fail fast），只有返回 falsy 才继续等 |

### 两套配置：`useFakeTimers(...)` 与 `fakeTimers`
`vi.useFakeTimers()` 会接管后续对 `setTimeout` / `setInterval` / `clearTimeout` / `clearInterval` / `setImmediate` / `clearImmediate` / `Date` 的调用，直到 `vi.useRealTimers()`。底层是 `@sinonjs/fake-timers`。

**默认不 mock `process.nextTick` 和 `queueMicrotask`**，要显式开启：

```js
vi.useFakeTimers({ toFake: ['nextTick', 'queueMicrotask'] })
```

- `toFake`：指定要 mock 哪些；`toNotFake`：指定保留哪些原生
- **两者不能同时指定**
- `toNotFake` 会始终排除 `nextTick` 和 `queueMicrotask`，要 mock 这两个只能用 `toFake`

配置项（`config/faketimers`）：

| 选项 | 默认 | 作用 |
| --- | --- | --- |
| `shouldAdvanceTime` | `false` | 让 mock 时间跟随真实系统时间自动前进 |
| `advanceTimeDelta` | `20` | 配合上一项，真实时间每走 20ms，mock 时间走 20ms |
| `loopLimit` | `10000` | 无限 interval 的保护阈值 |
| `shouldClearNativeTimers` | `true` | 启用假定时器时是否清掉原生定时器 |
| `fakeNodeBuiltins` | `false` | 5.1.0+，mock `node:timers` / `node:timers/promises` |
| `now` | `Date.now()` | 起始的 Unix 时间戳 |

### 已知限制（官方明写）
1. **`--pool=forks` 下不支持 mock `nextTick`**：Node 在 `node:child_process` 内部用 `process.nextTick`，mock 后会挂死；`--pool=threads` 下正常
2. **`toFake` 与 `toNotFake` 互斥**
3. **无限 interval 保护**：`runAllTimers` 若遇到不停止的 interval，会在 **10000 次尝试后抛错**（由 `loopLimit` 配置）
4. **`useRealTimers()` 会丢弃所有已排定的定时器**（原文：*All timers that were scheduled before will be discarded.*）——不是「保留但改用真实计时」
5. **Jest 的 legacy timers 不支持**：官方迁移页只有一句 *Vitest doesn't support Jest's legacy timers*，`jest.useFakeTimers('legacy')` 不能平移

> 「在 `beforeEach` 启用、`afterEach` 恢复」是官方**示例代码**的写法，官方没有给出明文建议句——但这是必须做的，否则 mock 状态会污染后续测试。

### 典型场景：debounce
```js
it('debounce 只在停止输入后触发一次', async () => {
  vi.useFakeTimers()
  const spy = vi.fn()
  const debounced = debounce(spy, 300)

  debounced('a')
  debounced('ab')
  debounced('abc')
  expect(spy).not.toHaveBeenCalled()

  vi.advanceTimersByTime(300)
  expect(spy).toHaveBeenCalledOnce()
  expect(spy).toHaveBeenCalledWith('abc')

  vi.useRealTimers()
})
```

## 我的理解 / 类比
真实定时器像**看着沙漏等**：沙漏是真的在漏，你只能干等，而且每台机器的沙漏流速还略有不同。
假定时器像**把沙漏换成一个旋钮**：想让它漏多少漏多少，一瞬间就能走完；但旋钮归你管，**用完必须拨回「真实沙漏」**，否则下一个测试还在用你手上这只假沙漏。
