# 移动端适配

## 一句话定义
移动端适配是**同时回答三层问题**：① **地基**（视口怎么声明）② **单位**（尺寸怎么写）③ **策略**（界面怎么随屏幕变化）。三层任缺一层，方案都不完整。

## 要点

### 三层模型
| 层        | 回答什么问题                                           | 可选手段                                        |
| -------- | ------------------------------------------------ | ------------------------------------------- |
| ① **地基** | 浏览器把「1 个 CSS 像素」定义成多大 —— 这同时决定了 `vw` / `rem` 的语义 | `<meta name="viewport">`；**动态改写缩放**（已退场，见下） |
| ② **单位** | 长度值用什么单位表达                                       | `px` / `rem` / `vw` / `%`                   |
| ③ **策略** | 同一条 CSS 在不同屏幕上怎么表现                               | 媒体查询、Flex / Grid、容器查询、`clamp()`、**整页等比缩放**  |

关键前提：**「媒体查询 + rem」不是两个并列方案，而是「③ 选媒体查询 + ② 选 rem」的一个组合**（俗称 flexible 方案）。把不同层的手段当成互斥选项来比较，是这类讨论最常见的框架错误。

### 方案全景
| #   | 方案       | 缩放 / 适配载体                           | 运行时依赖            | 详见                                    |
| --- | -------- | ----------------------------------- | ---------------- | ------------------------------------- |
| ① | 响应式 / 断点 | 媒体查询切换布局（**CSS 原生**） | 无 | [[媒体查询]]（原子化框架里的写法见 [[断点变体]]） |
| ② | 流式 / 弹性 | 百分比 + Flex / Grid + `min/max/clamp` | 无 | [[Flex 布局]] + [[CSS 数学函数]] |
| ③   | rem 等比缩放 | **动态根字号**（`1rem = 视口宽 / 10`）        | 需要 JS 或 `calc()` | [[rem 适配]]                            |
| ④   | vw 等比缩放  | 单位本身就是视口百分比                         | 无（构建期完成）         | [[vw 移动端适配]]                          |
| ⑤   | 混合（现代生产） | vw / rem + **封顶** + 断点修字号           | 无                | [[vw 移动端适配]]                          |
| ⑥   | 容器查询     | 按最近的**查询容器祖先**尺寸，而非视口               | 无                | [[容器查询]]                              |

- 另有一条同思路的实现：**小程序 `rpx`**（750rpx = 屏幕宽，由容器在运行时换算）—— 相当于把 ④ 的换算从**构建期**搬到**运行时**，因此不需要 PostCSS 插件。
- ③ 与 ④ **不是两代技术，而是同一件事（等比缩放）的两种载体**：③ 多一层「根字号」间接层，换来「能被 `clamp` / 媒体查询拦截」；④ 少这一层，换来「不需要 JS、不需要运行时」。

### 地基免疫性（核心规律）
> **视口比例单位（`vw` / `%` / `rem`）对地基变化「免疫」** —— 它们本来就是视口的百分比（`rem` 则是「被绑定到视口的根字号」），地基怎么变，它们跟着变，**物理尺寸不变**。
> **绝对单位 `px` 与媒体查询断点「绑定」地基** —— 地基一动，它们**整体搬家**。

以 iPhone 6（**375 逻辑 pt = 750 物理 px**，dpr 2）为例，样式一个字节都不改，只换地基：

| 样式 | 地基 A：`width=device-width`（布局视口 **375 CSS px**；1 CSS px = 2 物理 px） | 地基 B：classic flexible `initial-scale=0.5`（布局视口 **750 CSS px**；1 CSS px = 1 物理 px） |
| --- | --- | --- |
| `width: 50vw` | 187.5 CSS px = **375 物理 px** | 375 CSS px = **375 物理 px** ✅ **不变** |
| `width: 100px` | 100 CSS px = **200 物理 px** | 100 CSS px = **100 物理 px** ❌ **减半** |
| `font-size: 16px` | 32 物理 px | **16 物理 px** ❌ 减半 |
| `border: 1px` | 2 物理 px | **1 物理 px**（更细） |
| `@media (max-width: 480px)` | ✅ 命中（375 ≤ 480） | ❌ **不命中**（750 > 480），断点整体偏移 |

- **同一个 vw 值，在不同地基下含义不同**：`4.26667vw` 在地基 A 下是 16 CSS px，在地基 B 下是 32 CSS px —— 但两者**物理尺寸一致**。所以「px 换成 vw 是多少」这个问题，**脱离 `<meta name="viewport">` 就没有完整答案**。
- **混用地基 + 混用单位的代价**：vw 写的那部分几乎看不出变化，而所有 `px` 写的东西（字号、第三方组件库、1px 边框）会整体缩一半，媒体查询断点全部错位。
- **顺带解释一段历史噪音（分析）**：classic 方案下视口被整体缩放，页面里**每一个 px（含第三方组件库）都自动等比缩放**，所以那个年代不需要给组件库配尺寸黑名单；而 ③/④ 方案只转换插件看得见的 px，于是第三方库才需要黑名单、`exclude` 或「rem→px→vw」补救。**第三方库的处理责任，是从地基从「整体缩放」换成「局部转换」那一刻转移到配置文件里的。**

> ⚠️ **依据标注**：表中「地基 B 的布局视口 = 物理宽度 750」是**推论** —— 依据 classic flexible 源码里的算术 `if (width / dpr > 540) { width = 540 * dpr }`（它把取到的宽度除以 dpr 才得到逻辑宽度）。「地基免疫性」这张对照表本身是**归纳**（由 `vw` / `%` 的视口百分比定义与 `rem` 的根字号定义推出），**非规范原文**。

### 选型
| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 营销页 / 单端 H5（设计稿 1:1 还原） | ④ vw + **封顶** + 字号兜底 ✅ | 无运行时依赖，构建期一次完成 |
| 需要全局「一键封顶 / 区间限制」或要兼容老设备 | **纯 CSS rem**（`html { font-size: calc(100vw / 10) }` + `clamp`） | 保留 rem 的可拦截性，同时甩掉 flexible 的 JS |
| 中后台、PC + 移动同构 | 响应式（① + ②）❌ **不做全局缩放** | 等比缩放会把桌面端整页撑爆 |
| 组件库 / 设计系统 / 跨容器复用 | ⑥ 容器查询 + 响应式 | 组件不该关心自己在哪个视口 |
| 小程序 | `rpx` | 平台已内置 |

> 这张表是**取舍判断**（依据各行「理由」中的机制；机制部分已核实），不是规范结论。

## 已退场的做法

### ① 动态改写 viewport 缩放（classic `lib-flexible`）
- 做法：把 `<meta viewport>` 的 `initial-scale` 设成 `1/dpr`，将布局视口撑成**物理宽度**，使「1 CSS px = 1 物理像素」。
- 退场依据：`amfe/lib-flexible` README 原话——「由于 `viewport` 单位得到众多浏览器的兼容，`lib-flexible` 这个过渡方案已经可以放弃使用，不管是现在的版本还是以前的版本，都存有一定的问题。建议大家开始使用 `viewport` 来替代」。
- 现代写法：`<meta name="viewport" content="width=device-width">` —— MDN 现行文档明确说明 **`initial-scale=1` 通常不必写**（省略时浏览器自动决定初始缩放），只在内容溢出导致「不希望的缩小」时才加。
- ⚠️ 注意：`maximum-scale=1` / `user-scalable=no`（禁缩放）是同一个年代的产物，**不要照抄**。
- 上述"退出"和"现代写法"的完整叙述见 [[vw 移动端适配]]。

### ② 把字号交给缩放体系
- 依据：WCAG 1.4.4 的技术 F94 原文——「As these units are relative to the viewport, it means they cannot be resized by zooming or adjusting text-size.」字号写 vw 时，用户放大 200% 会让视口 CSS 宽度减半，一乘一除，**物理尺寸原地不动**。
- 务实做法：**布局宽高可以用 vw / rem，字号留在 `px` / `rem`，或用 `clamp()` 设上下限**。
- **存疑（依据 F94 测试程序）**：禁用页面缩放（`maximum-scale=1` / `user-scalable=no`）同样属于无障碍欠债 —— F94 的测试程序把「浏览器 zoom 功能」列为必须能把文字放大到 200% 的手段。
- 细节与生态现状见 [[vw 移动端适配]]。

## 我的理解 / 类比
`<meta name="viewport">` 决定的是**坐标系**（1 个 CSS 像素有多大、视口有多宽），`vw` / `rem` / `%` 是**坐标系里的比例**，`px` 是**绝对长度（度量衡）**。换地基 ＝ 换坐标系：**比例不动，绝对长度搬家**。所以「一半屏幕宽」这个诉求在任何坐标系里都成立，而「100px」这个诉求会随坐标系漂移——这正是 ③/④ 类方案把设计稿单位全部换成比例单位的根本动机。
