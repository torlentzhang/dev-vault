# 视口单位

## 一句话定义
视口单位是以视口尺寸为基准的相对长度单位，`1vw = 视口宽度的 1%`；这里的「视口」指**布局视口**，其语义由 `<meta name="viewport">` 决定（见 [[meta viewport]]）。

## 要点

### 静态视口单位
| 单位 | 含义 |
| --- | --- |
| `vw` | 布局视口**宽度**的 1%，`100vw` = **整个布局视口宽度** |
| `vh` | 布局视口**高度**的 1% |
| `vmin` | `vw` 与 `vh` 中**较小**的那个 |
| `vmax` | `vw` 与 `vh` 中**较大**的那个 |

- `100vw` 指的是**整个布局视口**，不等于「用户此刻能看到的宽度」——两者的差额就是滚动条（见下节）。
- 基准本身由 `<meta name="viewport">` 决定：375 CSS px 的布局视口下 `1vw = 3.75px`；换一种地基声明，同一个 `vw` 的物理含义就会变。基准怎么变、以及为什么换地基后 `vw` 的物理尺寸反而不变，见 [[meta viewport]] 与 [[移动端适配]]。

### 动态视口单位：`svh` / `lvh` / `dvh`
| 单位 | 含义 |
| --- | --- |
| `svh` | **小**视口 —— UA 界面**全部展开**时的高度（三者中最小） |
| `lvh` | **大**视口 —— UA 界面**收起**时的高度（三者中最大） |
| `dvh` | **动态**视口 —— 随 UA 界面**实时变化** |

- **解决的问题**：iOS Safari 上 `100vh` 把 URL 栏区域也算进去，导致底部内容被遮挡 / 多出滚动。
- **支持**：Chrome/Edge 108、Safari/iOS 15.4、Firefox 101、Samsung Internet 21；MDN Baseline 标记 widely available（2022-08）。（支持数据取自 caniuse，其快照当时已到 Chrome 157 / Safari 26.x。）
- **同族**：还有 `dvw`、`svb`、`dvi` / `dvb`（逻辑轴）等。
- **坑**：
  - `dvh` 随滚动实时重算会引起**布局抖动 / 掉帧** → 固定元素优先用 `svh`，只在必要时用 `dvh`。
  - Opera Mini、UC、QQ、百度浏览器仍不支持，需要 `100vh` 或 JS 兜底。

### `100vw` 的滚动条坑
CSSWG 邮件里对旧决议后果的复述：

> viewport units would not subtract the size of root scrollers' scrollbars... `width: 100vw` will overflow with `overflow: scroll`; you'll get horizontal scrollbars

2023-11 会议 **RESOLVED**：若 `overflow: scroll` 设在**根元素**上（不是从 `body` 传播来的），解析 `vw` 时要**计入默认滚动条宽度**，并考虑 `scrollbar-gutter` / `scrollbar-width`；**媒体查询里忽略这些**。

由此（推论）：

- 在带**经典滚动条**的桌面环境下，`calc(100vw / 10)` 会比 `document.documentElement.clientWidth / 10` **略大**（差额是一个滚动条宽度），`100vw` 也容易撑出横向滚动条。
- **该行为已在 2023 年底被 CSSWG 决定修改，因此会因浏览器版本而异** —— 这是规范与实现**正在变化**的点，不要当成稳定事实依赖。
- 移动端（覆盖式滚动条）基本无感。

> ⏳ **待观察**：`100vw` 与 `clientWidth` 是否等价，取决于上面这条决议在各浏览器的落地进度；落地前，纯 CSS 里用 `calc(100vw / 10)` 做根字号会在桌面端偏大。

## 我的理解 / 类比
- `vw` / `vh` 是「按视口百分比量」的尺子：刻度本身就是视口，所以视口一改、量出来的 CSS 值就跟着改，**物理尺寸却不动**。
- `dvh` 是「视口本身会呼吸时的实时读数」：读数一直跟着地址栏伸缩走，精确但每帧都要重算。
- `svh` 是「按最小可用范围量」：宁可底部留一点白，也不让内容被地址栏挡住。
