# npm 语义化版本号（SemVer）

## 一句话定义
SemVer 用 `主.次.修` 三段数字表达"兼容性变化"，npm 又在此基础上用范围符号（`^` `~` `*`）声明"允许装哪个区间的版本"——这是 npm 依赖管理的地基。

## 要点
- **三段数字的含义**（判定标准只有一条：是否向下兼容）
  - 主版本 MAJOR：做了**不兼容**的 API 变更 → `1.4.0 → 2.0.0`
  - 次版本 MINOR：向下兼容地**新增功能** → `1.3.2 → 1.4.0`
  - 修订 PATCH：向下兼容地**修 bug** → `1.4.0 → 1.4.1`
- **预发布版本**：`1.0.0-alpha.1`，用 `-` 接 `.` 分隔标识符，**永远低于**对应正式版；预发布之间按 ASCII 逐段比（`alpha < alpha.1 < beta`）
- **构建元数据**：`1.0.0+build.5114`，用 `+` 开头，**不参与版本比较**，只是同版本不同构建的标注
- **npm 依赖范围符号**（写在 package.json 的是"允许范围"，不是"装哪个"）
  - `^2.2.1` 锁主版本，允许次版本+修订（`>=2.2.1 <3.0.0`）
  - `~2.2.1` 锁次版本，只允许修订（`>=2.2.1 <2.3.0`）
  - `2.2.1` 精确版本；`*` / `""` / `2.x` 通配；`>` `<` `-` `||` 区间与或
- **安装时实际发生**：`npm install` 在范围内挑**最新版**装进 `node_modules`，并把确切版本写进 `package-lock.json` 锁定，保证别人装到同一棵依赖树
- **dist-tags（发行标签）**：`npm publish` 默认打 `latest`，`npm install foo` = `npm install foo@latest`；发 beta 用 `--tag next`，需显式 `npm install foo@next` 才拿得到

## 我的理解 / 类比
把版本号想成一栋酒店的 **楼号.楼层.房间号**：主版本是"哪栋楼"——搬家（跳楼）意味着大动、旧路线全废；次版本是"哪层"——楼没变，只是多了几间房；修订是"具体房间"——同一间房翻新了一下，住法不变。预发布版本 `1.0.0-alpha` 就是"房间还没交付"，再怎么样也排在 `1.0.0` 前面。

## 常见坑
- **`0.y.z` 是开发期免责声明**：主版本为 `0` 时任何变更都不承诺兼容，所以 `^0.2.1` 被 npm 收窄成 `>=0.2.1 <0.3.0`（只锁次版本），`0.2.0 → 0.3.0` 可能破坏性升级。
- **`^` 永不跨主版本**：`^2.2.1` 不会自动升到 `3.0.0`（那是破兼容的）；大版本更新要手动改范围。
- **默认不拉预发布版本**：`^1.2.3` 不会主动装 `1.3.0-beta` 或 `1.2.4-rc`，除非范围里显式写了预发布标识。

## 实战建议
- 写库时严格遵守 SemVer：破兼容必跳主版本，别让使用者踩暗坑
- 应用项目靠 `package-lock.json` / `pnpm-lock.yaml` 把整棵树锁死；`^` 是给"库声明依赖范围"用的，团队装依赖靠 lock 文件而非范围赌博
- `0.x` 阶段升级要谨慎，先看 changelog 再动
- 临时要跑某个确定版本的工具：`npx some-tool@1.2.3`（CI 里必须锁版本，避免行为漂移）
